为什么 / the gap

逆向的瓶颈不是模型不够聪明，
是工作流断在四个地方

上下文

一次 RE 任务的 strings / hexdump / 反编译输出 动辄几十万字符。塞进对话就爆窗口，不塞就等于没分析。

工具

file、strings、entropy、carve、apk、frida…… 每次都要人肉拼命令。模型知道该干什么，但手够不到。

信任

把 shell 交给模型，要么全放开（rm -rf 就在一次 hallucination 之外），要么全关死，退化成聊天。

可复现

解出来了，但过程留不下来。第二天问"当时怎么定位到那个校验函数的"，只能重来。

这四条都不是"换个更强的模型"能解决的问题 —— 它们是宿主端的工程问题。

定位 / scope

一个小而完整的逆向 Agent 宿主 ~11k 行 TypeScript · 38 个模块 · 0 运行时依赖（bun 原生）

it is它是

  • 一个 Agent Loop：模型 → 工具 → 结果 → 继续，直到收敛
  • 一层 Provider 适配：6 种 wire format 归一成一个接口
  • 一套 逆向专用工具表：triage / entropy / carve / apk / frida 模板
  • 一条 安全边界：分级审批 + 危险模式拦截
  • 一份 append-only JSONL：每一步都能回放、续跑

it is not它不是

  • 不是 IDA / Ghidra 的替代 —— 它调度这些工具，不重写它们
  • 不是通用编码 Agent —— 系统提示词、工具、技能全部围绕 RE 收敛
  • 不是一个 TUI 框架 —— 刻意比 oh-my-pi 小一个量级
  • 不是自动化攻击工具 —— 默认无网络、无写入，只服务授权场景

设计取向：宿主端做重，模型端做薄。上下文治理、安全策略、可观测性、会话持久化都在本地代码里，换任何模型都成立。

核心 01 / the loop

Agent Loop：一个循环，四个不变量 src/core/agent-loop.ts · 494 行，是整个项目唯一的控制流

prompt compact provider
tools approval tool_calls
  • 不变量 1：每个 tool_call 一定有对应的 result —— 包括被 ^C 打断的那次。否则严格的 chat API 会拒绝整段历史。
  • 不变量 2：磁盘上的 transcript 永远完整，被裁剪的只是发出去的那份视图。
  • 不变量 3：中断是一种结果，不是异常 —— 写入 [interrupted by operator] 后正常返回。
  • 不变量 4：计划面板纯观测，不参与调度，坏掉也不影响一次运行。
agent-loop.ts删减后的主干
for (; turns < maxTurns; turns++) {
  // 只裁剪"发出去的视图"，磁盘不动
  const view = compactHistory(messages, {
    budgetTokens: provider.contextBudgetTokens
  });

  const res = await provider.complete({
    system, messages: view.messages, tools,
    workspace, signal, onProgress
  });

  if (res.toolCalls.length === 0) return finish(turns);

  for (const call of res.toolCalls) {
    // 分级审批：tier 由工具声明，
    // 命令级风险由工具内部再报一次
    await requestApproval({
      tool: call.name,
      tier: tierForRisk(tool.risk)
    }, ctx);

    const out = await tool.execute(call.arguments, ctx);
    await pushToolResult(call, out.content);
  }
}

核心 03 / the unusual one

把本地 Codex / Claude CLI 当成 provider 用 src/providers/cli-tmux.ts · 546 行 —— 这是整个项目最"不常规"的一层

一次 turn 的生命周期
1. 预检登录态  codex login status / claude auth
   └ 先 unset OPENAI_API_KEY / ANTHROPIC_API_KEY，
     免得过期的环境变量顶掉本地 CLI 的登录

2. 落盘 prompt  runDir/prompt.txt（首轮全量，
     后续只发 delta —— CLI 自己续同一个 session）

3. 生成 runner.sh (mode 0700)，tmux 起一个
     分离会话执行它 → stdout / stderr / exit 三个文件

4. StdoutTail 实时 tail JSONL：
     thinking · tool · usage · plan · final
     → 直接喂给 HUD 和 trace，不用等命令结束

5. 收敛：读 exit code，优先取解析出的 final message
     ^C → 杀掉 tmux 会话，且不回落成重跑一次

fallback tmux 不可用时直接 spawn，同一份 runner.sh

why为什么值得这么绕

  • 复用登录态：用你已经付过费的 Codex / Claude Code 订阅，而不是再烧一份 API token
  • 白拿子 Agent 的能力：CLI 自带的检索、编辑、沙箱在它自己那侧执行，宿主只负责编排
  • 拿到原生事件：Claude 的 TaskCreate/TaskUpdate、Codex 的 plan_update 都在这条流里，计划面板因此对默认配置就生效

cost代价，说清楚

  • 这类 provider 恒定返回 toolCalls: [] —— 工具调用发生在子 CLI 内部，宿主的 23 个工具此时只作为 prompt 里的能力说明
  • 因此宿主端审批对它不生效，安全边界由子 CLI 的 sandbox 承担（codex 默认 --sandbox read-only）
  • 要完整的宿主端管控，就走 *-api 直连档
核心 04 / routing

planner 想，executor 做 —— 两个模型分工

routeProvider()
role=planner   →  config.plannerProvider   默认 codex
role=executor  →  config.executorProvider  默认 claude
role=auto      →  提示词分类器
                 命中"运行/读取/列出/grep/strings/
                 inspect ./…"等执行意图 → executor
                 否则 → planner（分析与规划）

显式覆盖：/agent grok   → 锁死到某个 provider
恢复路由：/agent auto

分类器同时匹配中英文关键词 —— 因为真实使用里，操作者会随手打"跑一下 ./chall"。

planner · codex

逆向推理、可利用性判断、解题路径规划。跑在 --sandbox read-only 下 —— 规划阶段本来就不该改任何东西。

executor · claude

低敏感度执行：文件检查、命令跑批、结果归纳。它的会话跨轮次持续复用（cliResumeSession），所以增量只发 delta。

第三方视角

/agent grok 让另一个模型复核解题计划的盲点；knowledgeProvider 单独指派一个模型做知识检索归纳。

核心 07 / policy

两个输入决定一次调用能不能跑 工具的 tier（read / write / exec） × 会话的审批模式

模式自动放行需要确认
yolo全部无 —— 只用于无人值守批跑
safe 默认各 tier 均放行命中安全模式的命令
writeread + writeexec 类工具，以及安全模式
always-ask只有 read其余全部

安全模式优先于"总是允许"

允许了 run_command 不等于允许 rm -rf /。命令级检查在工具内部做 —— 那是唯一知道真实命令文本的地方。

src/security/policy.ts
destructive  rm -rf · dd if= · mkfs · diskutil erase
             shutdown · reboot · sudo · > /dev/disk*
network      curl wget nc nmap ssh scp rsync socat dig… 需 --allow-network
sensitive    .ssh .aws .gnupg keychain id_rsa password
             secret token → 需 --allow-sensitive
默认策略：读只在 workspace 内 · 写需 --write
          网络关 · 敏感路径关 · 破坏性命令直接拦

没人可问的时候

--print、管道、CI 里无法弹确认框 —— 此时"需要确认"降级为带原因的拒绝，而不是默默放行。

核心 08 / context

逆向输出巨大，但窗口是固定的

pass 1省略工具结果体

旧的工具输出正文被折叠，只留第一行做指针：
[older strings result elided: 84213 chars. First line: …]

调用与参数完整保留 —— 模型仍然知道"我做过这件事"。

pass 2丢弃最老的完整轮次

从头开始整轮丢弃，替换成一条 [context compacted] 标记。一次工具调用永远不会和它的结果被拆散。

/compact模型级摘要

前两遍是机械的、无损语义的。/compact 则请模型写一份简报并从简报重启 —— 细节留在 JSONL 里，工作历史轻装上阵。

预算与观测
/context   ≈12400 tokens of 48000 budget (25%) · 42 msgs
/compact   折叠成简报后重启
/compact codex  指定用某个 provider 写摘要

默认预算 48k / provider 可配 contextBudgetTokens
token 估算：拉丁 ~4 字符 / CJK ~1.5 字符 一个 token
——刻意不引入分词器，够驱动预算就行

大输出不进上下文

超过 --max-output（默认 24000 字符）的工具输出只保留头 + 尾，全文写进 sessions/artifacts/，并把路径交给模型 —— 它可以再用 read_file / grep 精确取需要的那段。

这一条对逆向尤其关键：一次 strings 就能顶掉整个窗口。

实现过程 / one real decision

PLAN 面板：约束怎么倒逼出方案 docs/plans/2026-07-26-plan-panel-design.md · 原始设计文档节选

问题

双模型分工，但操作者看不见模型在计划什么。终端里只有 spinner 和工具调用行 —— 一次多步 RE 任务跑到哪、还剩什么，全靠猜。

约束（决定方案的关键事实）

默认两个 provider 都是 cli-tmux，而它恒定返回 toolCalls: [] —— 宿主侧的 update_plan 在默认路径上永远不会被触发。

但两个 CLI 都会各自产出计划，而且都流经已经在 tail 的那条 JSONL。

方案

以 CLI 事件流采集为主（默认配置即生效，且能拿到执行中的实时状态变更），宿主侧 update_plan 为辅（覆盖真 API provider），两条路汇入同一个 PlanTracker。

范围：纯可观测。不改 AgentLoop 控制流，计划不参与调度。

三条解析路径，一个 PlanTrackersrc/providers/stream.ts
Claude · Task*     TaskCreate{subject} + TaskUpdate{taskId,status}，id 由 tool_result 文本 "Task #N created successfully: X" 绑定
Claude · TodoWrite type:"assistant" → content[] 中 tool_use && name==="TodoWrite" → input.todos[]（兼容旧壳）
Codex              update_plan ×33 / plan_update ×7 / todo_list ×1 —— 新旧事件外壳都存在，必须都兼容
host               update_plan 工具 → 覆盖 claude-api / codex-api / deepseek / glm 等直连 provider

这页想说明的不是这个功能本身，而是这类项目的常态：真正决定方案的从来不是"想要什么"，而是"底层事实允许什么"。

  • 成本：分诊、解码、carve 这类确定性操作没有让模型参与的必要
